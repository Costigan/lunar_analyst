# Great-Circle Paths on the Moon in Oblique Stereographic Coordinates  
## Problem Statement, Numerical Issues, and GPU-Friendly Solution

---

## 1. Problem description

A visible "line" artifact was observed in shadow maps generated from the quadtree horizon generator. The artifact manifested as a sharp discontinuity in horizon elevation angles at the boundary between internal processing patches (specifically at x=4095/4096), despite the terrain being continuous.

- **Observed:** Horizon at Azimuth 347.25 differed significantly between Observer(4095, 860) and Observer(4096, 860), which are adjacent pixels.
- **Impact:** Produced artificial lines in lightmaps/shadows used for path planning.
- **Location:** Lat ~85.4°S (VIPER mission area).

## Diagnosis & Root Cause

### 1. Compact Mode Approximation
The QuadTree generator implemented a "Compact Mode" optimization for latitudes < 89° (previously considered "non-polar").
- **Mechanism:** In Compact Mode, the algorithm computes a *single* ray trajectory (polynomial) for the center of a 128x128 pixel patch.
- **Assumption:** It assumes that the ray's shape and direction in *Grid Space* are translation-invariant across the patch (i.e., you can just slide the start point without rotating the ray).

### 2. Grid Convergence Failure
At high latitudes (85°S), this assumption fails due to **Grid Convergence**—the angle between True North (geodetic) and Grid North (projected map).
- The projection is Polar Stereographic.
- Grid Convergence changes as a function of longitude (and thus X/Y position on the map).
- Across a single 128-pixel patch width (~2.5 km), the Grid Convergence changes by approximately **0.052°**.

### 3. The Artifact
Because Compact Mode used the *patch center's* Grid Convergence for all pixels in the patch:
- Pixels at the right edge of Patch N used a ray rotated by $\gamma_{center\_N}$.
- Pixels at the left edge of Patch N+1 used a ray rotated by $\gamma_{center\_N+1}$.
- At the boundary (x=4095 to 4096), the ray direction effectively jumped by $\Delta\gamma \approx 0.052°$.
- Over a 100km horizon distance, a 0.05° rotation shifts the sampling path by ~90 meters, causing the ray to hit different terrain features.

## 2. Solution Attempt #1: Disable Compact Mode

Disabling "Compact Mode" (moving to "Full Mode") solved the horizon discontinuity artifact but increased computati
on time by orders of magnitude (from seconds to hours).  The increase was on the CPU side in generating all of the polynomials.

We need a solution that retains the performance of Compact Mode while eliminating the grid convergence artifacts at high latitudes.

## 3. Solution Attempt #2: Replace the polynomials with analytical solutions based on assuming oblique stereographic projections only.

Rays from an observer pixel are great-circles from that point.  The goal is to compute **points along a great-circle path on the Moon**, starting from a known surface point and moving in a specified tangent direction, and to express those points in a **oblique stereographic map coordinate reference system (CRS)**.

The requirements are:

1. The path must follow a **true great circle** on a spherical Moon (no planar or rhumb-line approximations).
2. Output coordinates must be in the **oblique stereographic plane** (X, Y).
3. A third coordinate **Z** must represent the **vertical drop below the tangent plane at the start point**, measured along the surface normal at that point.
4. The effective radius at the start point is  
   \[
   R = R_{\text{Moon}} + h_0
   \]
   where \(h_0\) is the local elevation.
5. Points are generated by “walking away” from the start point until the **edge of the stereographic map** is reached.
6. The final algorithm must be suitable for **GPU execution**, where double-precision performance is poor or unavailable.

---

## 2. Classical (CPU) formulation

Let:

- \(\mathbf{p}\): unit surface normal at the start point  
- \(\mathbf{t}\): unit tangent direction at the start point  
- \(s\): angular distance along the great circle (radians)

The great circle on a sphere is parameterized as:

\[
\mathbf{r}(s) = R \left( \mathbf{p}\cos s + \mathbf{t}\sin s \right)
\]

### oblique stereographic projection (spherical, normalized)

For a projection from the north pole:

\[
X = \frac{x/R}{1 - z/R}, \qquad
Y = \frac{y/R}{1 - z/R}
\]

### Drop below the tangent plane

The tangent plane at the start point has normal \(\mathbf{p}\).  
The vertical offset from this plane is:

\[
Z(s) = \mathbf{p} \cdot (\mathbf{r}(s) - R\mathbf{p}) = R(\cos s - 1)
\]

This formulation is mathematically correct and convenient on the CPU.

---

## 3. Precision analysis

### 3.1 Why single precision fails in the classical form

Key numerical issues:

1. **Catastrophic cancellation**  
   For small \(s\):
   \[
   \cos s - 1 \approx -\frac{s^2}{2}
   \]
   For meter-scale motion on the Moon, this term is \(10^{-13}\)–\(10^{-12}\), which rounds to zero in `float`.

2. **Stereographic denominator near the map edge**  
   \[
   1 - z/R \rightarrow 0
   \]
   Single precision loses multiple bits of accuracy before reaching the edge.

3. **Trigonometric evaluation**  
   Accurate curvature and projection require more precision than `float` can reliably provide.

### 3.2 Consequence

The classical formulation **requires double precision** for:
- Angular parameter \(s\)
- Trigonometry
- Tangent-plane drop \(Z\)

This is unsuitable for GPUs with poor FP64 performance.

---

## 4. GPU-friendly reformulation

### 4.1 Key idea

Instead of parameterizing the curve by angular distance \(s\), parameterize it by:

\[
d = \text{distance in the stereographic (tangent) plane}
\]

This quantity is **exactly the radial coordinate of the stereographic projection** and avoids trigonometry and cancellation.

Relationship to angular distance:
\[
d = R \tan\left(\frac{s}{2}\right)
\]

---

### 4.2 Tangent-plane drop (stable form)

The exact vertical drop below the tangent plane as a function of \(d\) is:

\[
Z(d) = -\frac{2 d^2}{R + \sqrt{R^2 + d^2}}
\]

Properties:
- No subtractive cancellation
- Stable in single precision
- Correct quadratic behavior for small \(d\):
  \[
  Z \approx -\frac{d^2}{2R}
  \]

---

### 4.3 Projected X,Y coordinates

Because \(d\) is already a **stereographic plane distance**, the projected coordinates are:

\[
(X, Y) = d \, \hat{\mathbf{t}}_{xy}
\]

where \(\hat{\mathbf{t}}_{xy}\) is the tangent direction expressed in the local map plane.

Projection parameters (scale factor, central meridian rotation, false easting/northing) are applied **afterward** as simple linear transforms.

---

## 5. Map-edge radius

A oblique stereographic projection has no finite mathematical boundary, but a **practical map edge** is defined by a minimum latitude \(\phi_{\min}\):

\[
\rho_{\max} = 2 R k_0 \tan\left(\frac{\pi}{4} - \frac{\phi_{\min}}{2}\right)
\]

Where:
- \(k_0\) is the projection scale factor
- \(\rho_{\max}\) is the maximum allowed stereographic radius

This gives the termination condition for stepping along the great circle:

```c
## 6. Final GPU-ready (float-only) formulation

Assumptions

1. p and tLocal are orthonormalized on the CPU
2 .The Moon is treated as spherical
3. Projection parameters are applied explicitly

```
// GPU-safe, float-only formulation
// d  : stereographic-plane distance (meters)
// t  : unit tangent direction in local map plane
// R  : Moon radius + elevation at start point
// k0 : stereographic scale factor
// rot: 2x2 rotation matrix for central meridian
// fe : false easting / northing

float3 GreatCircleStereoFloat(
    float d,
    float2 t,
    float R,
    float k0,
    float2x2 rot,
    float2 fe
)
{
    // Stereographic plane coordinates
    float2 xy = d * t;

    // Apply CRS rotation, scale, and offset
    xy = mul(rot, xy) * k0 + fe;

    // Stable curvature drop
    float Z = -2.0f * d * d / (R + sqrt(R * R + d * d));

    return float3(xy.x, xy.y, Z);
}
'''

7. Summary

* The original great-circle + stereographic formulation is mathematically correct but numerically incompatible with single precision.
* The key failure modes are cancellation and near-singular denominators.
* Reparameterizing the path by stereographic plane distance eliminates trigonometry and second-order cancellation.
* The resulting formulation:
  * Uses only single precision
  * Is stable over lunar scale
  * Is ideal for GPU execution
* The map-edge radius provides a clean, projection-consistent termination condition.

This approach preserves the correct geometry of great circles on the Moon while meeting the practical constraints of GPU hardware.
