Most Likely Causes

1. Ray Start Point Translation Issues

In Compact Mode, we translate the ray start point from tile center to each pixel:

 startPx = seg.StartPixel.X + dCol * scaleRatio;
 startPy = seg.StartPixel.Y + dRow * scaleRatio;

Problem: If scaleRatio or the translation is wrong, adjacent pixels
could be sampling completely different terrain rather than slightly
offset versions of the same ray.

2. Polynomial Approximation Breakdown

The cubic polynomial is fitted for the tile center ray, but used for all pixels. At tile edges (±64 pixels from center), the approximation might be fundamentally invalid.
Evidence: You mentioned "large elevation differences" - suggests rays are hitting different terrain features entirely.

3. DEM Resolution/Scaling Mismatches

 float scaleRatio = primaryRes / activeRes;

Problem: If multiple DEMs have different resolutions, adjacent tiles might use different scaleRatio values, causing ray start points to jump.

Secondary Causes

4. Observer Height Discontinuities

Each pixel samples observer height from primary DEM:

 float obsTerrain = SampleBilinear(primaryPV.DataLevel0, ...);

If there are elevation jumps in the DEM data at tile boundaries, this creates artificial terrain steps.

5. Coordinate Transform Precision

At 85°S, coordinate transforms are numerically sensitive. Small precision errors could accumulate into large terrain sampling differences.

6. Pipeline Processing Issues

Maybe horizon generation is correct, but the shadow mapping pipeline has tile boundary artifacts when combining multiple horizon files.
