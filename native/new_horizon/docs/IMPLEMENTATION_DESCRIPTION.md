# Implementation Description & Analysis

This document details the inner workings of the Horizon Generation system, contrasting the "Reference" (Ground Truth) implementation with the "QuadTree" (Optimized) implementation. It serves to aid in debugging performance regressions and accuracy discrepancies.

## 1. Reference Implementation (Ground Truth)

**Files:** `horizongen/ReferenceHorizonGenerator.cs`, `horizongen/ReferenceRayEmulator.cs`

The Reference implementation operates on first principles using 3D vector mathematics in a Moon-Centered, Moon-Fixed (MCMF) coordinate system. It does **not** rely on map projections for ray marching mechanics, only for looking up terrain heights.

### Algorithm
1.  **Observer Setup:**
    *   The observer's position is defined by a Pixel $(x, y)$ in a specific DEM.
    *   This is converted to Latitude/Longitude $(\phi, \lambda)$.
    *   A 3D vector $\vec{O}$ (Observer) is created:
        $$ R = R_{moon} + \text{Elevation}(x,y) + \text{ObsHeight} $$
        $$ \vec{O} = (R \cos\phi \cos\lambda, R \cos\phi \sin\lambda, R \sin\phi) $$
    *   A rotation matrix $M$ is constructed to transform vectors from the local "Observer Frame" (likely ENU - East, North, Up) to the global frame.

2.  **Ray Marching:**
    *   For each azimuth $\alpha$:
        *   A direction vector $\vec{D}_{local}$ is created in the tangent plane: $(\cos(90-\alpha), \sin(90-\alpha), 0)$.
        *   This is transformed to global space: $\vec{D}_{global} = M \cdot \vec{D}_{local}$.
        *   The algorithm marches along this tangent vector by distance $d$:
            $$ \vec{P}_{walker} = \vec{O} + \vec{D}_{global} \cdot d $$
            *Note: This moves the "walker" off the sphere surface, along a straight line in space tangent to the observer.*
        *   **Stepping Strategy:** The distance $d$ is **not constant**. It is generated by `EnumerateErrorBoundSteps`, which uses an angular error budget to increase step size as the distance increases ($d_{next} = d_{current} + \text{step}$, where $\text{step}$ grows). This ensures higher sampling density near the observer (where angular resolution is critical) and sparser sampling far away.

3.  **Sampling & Slope:**
    *   To find the terrain height "under" the walker, the 3D position $\vec{P}_{walker}$ is converted back to Geodetic Lat/Lon $(\phi', \lambda')$. This effectively projects the point on the tangent ray down to the sphere.
    *   The DEM is sampled at $(\phi', \lambda')$ to get $H_{terrain}$.
    *   A new 3D point $\vec{P}_{caster}$ is constructed on the surface:
        $$ R' = R_{moon} + H_{terrain} $$
        $$ \vec{P}_{caster} = \text{SphericalToCartesian}(R', \phi', \lambda') $$
    *   The vector from Observer to Caster is computed: $\vec{V}_{diff} = \vec{P}_{caster} - \vec{O}$.
    *   This vector is transformed *back* to the local observer frame: $\vec{V}_{local} = M^{-1} \cdot \vec{V}_{diff}$.
    *   **Slope:** The elevation angle is calculated from the local vector components:
        $$ \text{Slope} = \frac{V_{local}.z}{\sqrt{V_{local}.x^2 + V_{local}.y^2}} $$

### Key Characteristics
*   **Accuracy:** Exact spherical geometry. Handles curvature naturally via 3D vectors.
*   **Performance:** Slow ($O(N)$ per ray). Requires frequent `sin/cos/atan` and coordinate transformations per step.

## 2. QuadTree Implementation (Optimized)

**Files:** `horizongen/QuadTreeHorizonGenerator.cs`, `horizongen/QuadTreeRayEmulator.cs`

The QuadTree implementation is designed for massive parallelism on the GPU. It attempts to approximate the complex geodesic path of the Reference implementation using curve fitting in 2D pixel space, allowing it to traverse a texture-based Min-Max QuadTree.

### Phase A: CPU Pre-calculation (`CalculateRaySegments`)
The GPU kernel cannot easily do Geodetic Lat/Lon projections. Therefore, the CPU pre-calculates the ray paths.

1.  **Geodesic Sampling:**
    *   The CPU traces the exact Great Circle path (the "shadow" of the Reference tangent ray on the sphere) for each azimuth.
    *   It generates a set of sample points $(s_i, x_i, y_i)$, where $s$ is the ground distance, and $(x, y)$ are DEM pixel coordinates.

2.  **Polynomial Fitting:**
    *   To compress this path for the GPU, it fits cubic polynomials to the pixel coordinates:
        $$ x(s) = x_0 + A_1 s + A_2 s^2 + A_3 s^3 + A_4 s^4 $$
        $$ y(s) = y_0 + B_1 s + B_2 s^2 + B_3 s^3 + B_4 s^4 $$
    *   It also fits a "Planar-to-Chord" cubic to map "Planar Map Distance" back to "True Chord Distance".

3.  **Modes:**
    *   **Compact Mode:** Used away from poles. Calculates *one* ray per azimuth at the tile center. Assumes all pixels in the tile use the same ray coefficients, just shifted by $(Pixel - Center)$.
    *   **Full Mode:** Used near poles (>89°). Calculates a unique ray for *every pixel* because the map projection distorts rapidly (Grid Convergence).

### Phase B: GPU Kernel (`QuadTreeRayCastKernel`)
The kernel runs purely in Pixel/Map space, consuming the polynomial coefficients.

1.  **State:** Tracks current distance $s$ (ground meters).
2.  **Position Evaluation:**
    *   Calculates $(px, py)$ using `EvalCubic(s)`.
    *   Calculates local tangent vector using `EvalCubicTangent(s)` for traversing the grid.
    *   **Stepping Strategy:**
        *   **Hierarchical:** Steps are determined by QuadTree blocks. If a block is empty/occluded, the step size is the distance to the block's exit boundary.
        *   **Level 0 (Leaf):** When drilling down to the finest resolution, the algorithm advances $s$ by approximately 1 pixel width (derived from the local tangent magnitude). This differs fundamentally from the Reference algorithm's geometrically growing steps.

3.  **Slope Calculation (The Approximation):**
    *   Unlike the Reference, the GPU does not do 3D vector math. It uses a spherical approximation:
    *   $\theta = s / R_{moon}$
    *   $H_{drop} = 2 R_{moon} \sin^2(\theta/2)$ (The geometric drop of the sphere surface from the tangent plane).
    *   $Z_{local} = (H_{terrain} \cdot \cos\theta) - H_{observer} - H_{drop}$
    *   $X_{local} \approx \text{ChordDist}(s)$
    *   $\text{Slope} = Z_{local} / X_{local}$
4.  **Hierarchical Traversal:**
    *   Reads the Min-Max Pyramid.
    *   Estimates if a block can be skipped by calculating the max possible slope for the block using the formula above.
    *   If `MaxBlockSlope < CurrentHorizonSlope`, the block is skipped.
    *   Otherwise, it drills down or steps forward.

## 3. Algorithm Comparison Summary

| Feature | Reference (Ground Truth) | QuadTree (Optimized) |
| :--- | :--- | :--- |
| **Space** | 3D Cartesian (Moon-Centered) | 2D Map Pixel Space + Height |
| **Ray Path** | Straight line in tangent space | Cubic Polynomial Curve $x(s), y(s)$ |
| **Sampling Points** | Geometrically growing (Angular Error Budget) | Spatial / Data Driven (Pixel & QuadTree Block) |
| **Slope Calculation** | Exact Vector Angle $\vec{V} \cdot \vec{Z}$ | Approx. Drop $2R\sin^2(\theta/2)$ |
| **Culling** | None (Brute Force) | Min-Max QuadTree (Pyramid) |
| **Execution** | CPU (Single Thread / Parallel.For) | GPU (Massively Parallel) |
| **Coordinate Sys** | Lat/Lon $\leftrightarrow$ Cartesian | Map Projection (Stereographic) |

## 4. Emulators & Debugging

**Files:** `horizongen/ReferenceRayEmulator.cs`, `horizongen/QuadTreeRayEmulator.cs`

The "Ray Emulators" are specialized, instrumented CPU versions of the core algorithms. They are designed to act as "White Box" probes, allowing developers to inspect the internal state of a single ray cast (e.g., sample points, intermediate slopes, coordinates) without modifying the high-performance production code or dealing with GPU debugging tools.

### Role
*   **Trace Generation:** They output CSV files detailing every step taken by the algorithm.
*   **Verification:** They allow comparing the *logic* of the QuadTree traversal against the *geometry* of the Reference implementation on a per-step basis.

### Potential Differences & Risks
*   **Double vs. Float:** The `ReferenceHorizonGenerator` uses `double` precision for most operations. The `QuadTreeRayEmulator` attempts to mimic the GPU's `float` precision behavior in its "kernel" logic but uses `double` for the pre-calculation phase. Discrepancies in rounding modes or precision can cause the emulator to diverge slightly from the actual GPU kernel (e.g., a block skipped in emulator might be visited in GPU, or vice versa).
*   **Stepping Logic:** The `QuadTreeRayEmulator` must perfectly replicate the GPU kernel's complex "skip vs. drill" logic. Any desynchronization here renders the debug trace misleading.
*   **Unified Step Mode:** Both emulators support a `unifiedStepMode` (fixed 1.2m steps) to force them onto a common grid for direct comparison. **This is artificial.** Neither production algorithm uses 1.2m steps. While useful for checking slope formulas, it does not reflect the actual sampling distribution of the production run.

## 5. Analysis: Why is the QuadTree algorithm slow?

The performance degradation likely stems from **Over-Complexity in the Inner Loop** and **Pre-calculation Overhead**.

1.  **Polynomial Evaluation Cost:**
The kernel evaluates two 4th-order polynomials (`EvalCubic` for X and Y) and their derivatives (`EvalCubicTangent`) at *every single step* (or sub-step during hierarchy traversal).
    *   Reference: `pos += dir` (Simple vector add).
    *   QuadTree: $x = x_0 + A_1 s + A_2 s^2 \dots$ (Many FMADs).
    *   *Impact:* The ALU intensity per step is extremely high compared to a standard Bresenham or DDA ray caster.

2.  **Full Mode CPU Bottleneck:**
If the "Full Mode" (per-pixel ray calculation) is triggered, the CPU must solve linear least-squares systems for $128 \times 128 \times 1440 \approx 23.5 \text{ million}$ segments. This will stall the pipeline significantly before the GPU even starts.

3.  **Hierarchy Failure (Thrashing):**
If the `AdaptiveEpsilon` or conservative bounds are too loose (negative epsilon mentioned in code comments: `COMPARISON_EPSILON = 0.0f`), the culling fails. The algorithm forces the kernel to visit Level 0 (leaf nodes) unnecessarily. Combined with the expensive polynomial stepping, this is slower than a naive linear search.

4.  **Register Pressure:**
The `RaySegment` struct contains ~16 floats. Loading this for every thread consumes significant register file space, reducing GPU occupancy (fewer active warps).

## 4. Analysis: Where are the slope discrepancies coming from?

The ~0.25° error is likely due to **Curvature Approximation Mismatches** and **Coordinate System Drift**.

1.  **Vertical Drop Formula:**
    *   **Reference:** Computes $Z$ exactly via dot product of 3D vectors.
    *   **QuadTree:** Uses $Z_{local} = H_{pix} \cos\theta - H_{obs} - 2R\sin^2(\theta/2)$.
    *   *Issue:* This formula assumes the "Vertical" at the caster is parallel to the radius vector of the observer rotated by $\theta$. However, the Reference slope is defined in the *Observer's Tangent Plane*. The term `bilinearH * cosT` attempts to project the terrain height onto the observer's vertical axis, but this is a simplification. At large distances (large $\theta$), the geometric interpretation of "elevation relative to observer tangent" diverges slightly from this formula.

2.  **Polynomial Drift:**
    *   The cubic polynomials $x(s), y(s)$ are fits. Over 1000km, a small fit error means the GPU samples a pixel slightly offset from the true geodesic.
    *   If the ray shifts by even 1 pixel (20m) into a valley or ridge, the resulting elevation $H_{terrain}$ changes, altering the slope significantly.

3.  **Observer Height Definition:**
    *   **Reference:** `Radius = MoonRadius + DemElevation + ObsHeight`.
    *   **QuadTree:** `ObsZ = DemElevation + ObsHeight`.
    *   If `DemElevation` is sampled differently (bicubic vs bilinear) or if the QuadTree's `obsZ` parameter doesn't perfectly match the exact radius used in the Reference vector setup, a constant bias appears.

4.  **Precision Loss:**
    *   `MapRes` estimation: The QuadTree code calculates `mapRes = (pixCol + pixRow) * 0.5`. If pixels are not square, or scale varies (Stereographic), treating $s$ (meters) as a uniform scalar to drive polynomial evaluation introduces error. The polynomial maps $s \to (x,y)$, but the *slope* calculation uses $s$ directly for curvature drop. If $s$ doesn't exactly match the true chord distance to the sample point, the curvature drop $2R\sin^2(s/2R)$ will be wrong.
