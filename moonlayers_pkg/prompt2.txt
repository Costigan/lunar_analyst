I want to extend the project in this directory in several ways:

- Add a way to add layers from a large list using text search
- Add a way to remove layers
- Keep the existing way to turn layers on and off
- Enable adding and removing layers programmatically (via calls to the MoonMap object)

This URL returns a list of available layers as json:
https://trek.nasa.gov/moon/TrekServices/ws/index/polar/searchItems?proj=urn:ogc:def:crs:IAU2000::30120&start=0&rows=1000

Look at ./trek-search-layer-response-clipped.json to see an example of what the server returns.
The layers are listed in response.response.docs

Also, for context, look at ./DEVELOPMENT_NOTES.md.

Ask any questions you have first, then
make a detailed plan for implementing these features.

----------------------------------------

1. This tool is an AnyWidget intended to be used in
marimo.  The layer search UI needs to work within that
context. I think the only option is a javascript-side
UI embedded in the map.

To achieve the goal of adding and removing layers
programmatically, I think there also needs to be a way
to fetch the list of layers in python code, to search
for layers that match a pattern and to add and/or
remove those layers from the AnyWidget.

2. I think we should ignore the productType field and
match on the productLabel, title and description
properties.  The match can be simple. We don't need a
way of controlling which fields are matched
against. If the pattern matches any of the fields,
then the layer matches.

I would like the search patterns to allow conjunction,
disjunction and negation. I'm flexible about how.

3. We need to support multiple layer source
types. They won't all be tiled rasters.

We don't need to let the user preview the layer metadata.

4. Yes, for programmatic removal of layers,
remove_layer(layer_id) is sufficient.  But there needs
to be a way to programmatically search for layers to
get the layer_id's.  Calling remove_layer(layer_id)
for a layer that is not currently in the set of layers
in the control should result in no error.

We don't need a history or undo capability.  Removal
should work through the layer switcher UI, if the
component used supports that.  If not, we should talk
more.

5. I don't understand this question: Keep track of all
available layers (from Trek API) vs. added layers
separately?  Yes, we should persist added layers and
which are visible across widget reloads.

We don't need a user interface operation for saving
and loading layer configurations.

We should allow marimo python code in cells that have
access to the variable holding the widget to request a
list of layers that can be saved in some way and that
can be given back to the widget to set its state.
Ideally, this would also save the viewport state as
well.  For this widget, the projection will always be
the south polar stereographic projection we've
discussed.

6. We don't need pagination for the search results. We
just need to display the title of the matching layers
in a list. It would be nice to have a tool tip that
gives the layer's id. It would also be nice to have a
right click menu with an option to see the description
on moon trek's website.

We don't need layer groups or categories.  We don't
need a limit on the number of layers added at a time.
We don't need a limit on the total number of layers
added in total, although we don't want more than 10.
